## 1. System Vision

**Type:** Web Application (SPA + API propia, mismo repositorio)
**Primary Users:** socios, encargado del material y junta (3 roles, ENT-001)
**Scale:** un club: decenas de socios, cientos de reservas; una sola instancia
**Key Constraint:** Stack fijo (REQ-C-002) y datos compartidos entre dispositivos (REQ-NF-001), por lo que hace falta un servidor con almacén propio.

> Una aplicación web en español. El navegador carga una SPA de JavaScript vanilla construida con Vite; esta habla JSON con una API Node que valida sesión y rol, aplica las reglas del dominio y guarda todo en una base de datos embebida del servidor. El dominio es JavaScript puro y sin I/O, por lo que se prueba con Vitest sin navegador ni base de datos.

## 3. Delivery Channels (Dimension 1)

**Decision:** Web responsive (SPA servida por Vite), usable en móvil y escritorio.
**Rationale:** REQ-NF-001 habla de «distintos dispositivos»; no hay requisito de app nativa.
**Alternatives considered:** SSR/MPA (rompe el perfil Vite-SPA), app nativa (coste sin requisito), PWA (no pedida).
**Trade-offs:** Sin modo offline; sin JS no hay aplicación.
**Frontend:** JavaScript vanilla con módulos ES, router por hash y render por funciones; sin framework (nada lo exige y el stack no lo pide). Revisable si la UI crece (clase R).

---

## 4. Architecture Style (Dimension 2)

**Decision:** Monolito modular en capas (hexagonal ligera), un único proceso Node.
**Rationale:** 4 módulos de contrato (API-001..004) y un solo equipo; el aislamiento se logra con capas, no con servicios.
**Alternatives considered:** microservicios y serverless (sobredimensionados), event-driven (`EVENTS-material.md` es informativo, sin bus).
**Trade-offs:** escalado vertical únicamente; un fallo del proceso corta todo el servicio.

```
 Navegador (SPA, src/ui)
      │  POST /api/<operación>  JSON · cookie de sesión HttpOnly
      ▼
 ┌────────────────────────── Proceso Node (plugin de Vite / servidor) ──────────────────────┐
 │ src/server/http   → sesión, rol (PERMISSIONS-MATRIX), validación de entrada, errores     │
 │ src/domain        → reglas puras (INV-*, SM-001/002, multa); recibe el reloj y repos     │
 │ src/server/repo   → base embebida (node:sqlite), transacciones, hash scrypt              │
 └──────────────────────────────────────────┬────────────────────────────────────────────────┘
                                            ▼
                                 data/club.db (disco del servidor)
```

Estructura de código (`code_paths: src/`): `src/domain/`, `src/server/`, `src/ui/`, `src/shared/textos.js` (único módulo de textos, REQ-C-001, literales VO-010). Tests en `tests/` reflejando esa estructura.

## 6. Data Strategy (Dimension 4)

**Primary Database:** SQLite mediante el módulo integrado `node:sqlite`, fichero `data/club.db`, modo WAL.
**Schema Approach:** SQL con migraciones numeradas `src/server/repo/migrations/NNN-*.sql` aplicadas al arrancar; sin ORM.
**Caching:** not needed.
**Rationale:** REQ-NF-001 pide un almacén de servidor compartido; la base embebida da transacciones ACID para INV-RES-001 (comprobar disponibilidad y escribir en una sola transacción `BEGIN IMMEDIATE`, sin sobre-reserva por concurrencia) y «sin escritura parcial» (`nfr/AVAILABILITY.md`).
**Alternatives:** PostgreSQL (servicio extra sin necesidad), fichero JSON (sin atomicidad), IndexedDB/localStorage (incumple REQ-NF-001).
**Tablas:** `cuenta`, `material`, `reserva`, `multa`, `sesion` (ENT-001..005). Restricciones en BD: `cuenta.correo` único, `material.nombre` único, `multa.reserva_id` único (INV-FIN-002), CHECK de estados (VO-004/005).
**Fechas:** texto `YYYY-MM-DD`, aritmética en días naturales UTC (sin horas; REQ-C-003). El «hoy» sale de un reloj inyectable.
**Ocupación:** `ocupadas(d)` se calcula por consulta sobre reservas Reservada/Entregada; sin contadores desnormalizados.
**Baja de unidades (RN-002):** `unidadesActivas` baja sin tocar reservas; puede haber días con más reservas activas que unidades. La interfaz del encargado (Ver hoy / Entregas) debe señalar esos días para que avise a mano; no hay notificaciones automáticas ni correo.
**Backup:** copia diaria del fichero (`.backup` de SQLite) por el operador; retención 30 días (cubre parte de COMPLY-001).
**Cuentas iniciales (RN-001):** script `npm run cuentas -- alta <correo> <rol>` (CLI para el encargado/operador, lee la contraseña por stdin); no existe ruta HTTP de alta.

## 7. Auth & Security (Dimension 5)

**Authentication:** correo + contraseña (API-001-01). Contraseñas con `crypto.scrypt` (N=2^15, r=8, p=1, sal aleatoria de 16 B por cuenta, comparación `timingSafeEqual`) → CRYPTO-001 e INV-ACC-001. Sesión **en servidor**: token aleatorio de 256 bits en cookie `HttpOnly; SameSite=Strict; Secure` (Secure fuera de localhost), tabla `sesion` con una fila por cuenta (INV-ACC-002), caducidad por inactividad 30 min y absoluta 12 h, cierre de sesión explícito (AUTH-002).
**Freno de intentos (AUTH-001):** contador por correo e IP: 5 fallos → bloqueo 15 min respondiendo siempre `E_AUTH_INVALID` (sin enumerar cuentas, AUTH-003).
**Authorization:** RBAC con tres roles + regla de fila «dueño» (INV-ACC-004). Tabla de permisos en código derivada de `PERMISSIONS-MATRIX.md`, **denegación por defecto** (AUTHZ-001). Reserva ajena e inexistente no deben distinguirse para un socio (AUTHZ-002); el código de error exacto lo fija el contrato (si choca con `E_RES_NOT_FOUND`/`E_FORBIDDEN_DATA`, es asunto del spec-auditor).
**Input validation (INPUT-001):** esquema por operación (tipos, longitud ≤ 100 en correo/material, enteros 1..1000 en unidades, `Dia` estricto `YYYY-MM-DD`), SQL siempre parametrizado, cuerpo JSON ≤ 16 KB.
**Encryption:** TLS terminado en el proxy inverso; HSTS; Node escucha solo en 127.0.0.1 detrás de él (DATA-001). Sin cifrado en reposo más allá del disco.
**CSRF:** SameSite=Strict + exigir `Content-Type: application/json` + comprobar `Origin` en las escrituras.
**Registro de seguridad (INCIDENT-001):** log JSON por línea de accesos fallidos y de acciones del encargado (entregar, devolver, multas, inventario) con actor, operación, id y marca de tiempo; sin contraseñas ni hashes.
**Compliance:** datos personales mínimos (correo); retención y derechos (COMPLY-001) quedan como decisión del club.

> Security audit findings incorporated: `audits/SECURITY-AUDIT-BASELINE.md` — THR-001, AUTH-001..003, AUTHZ-001/002, DATA-001, INPUT-001, CRYPTO-001, INCIDENT-001, SADR-001 tienen respuesta técnica aquí. Cambiar o restablecer contraseña no está en los requisitos: la CLI de cuentas lo cubre (`cuentas -- clave <correo>`) y no se añade pantalla.

## 8. API Design (Dimension 6)

**Style:** RPC sobre HTTP/JSON: una ruta `POST /api/<operación>` por operación de los contratos (`Style: operations`). Mapeo completo en `design/OPERATION-MAPPING.md`.
**Versioning:** none (cliente y servidor se despliegan juntos).
**Documentation:** los contratos `spec/contracts/API-*.md` son la fuente; sin OpenAPI.
**Errores:** `{ ok:false, codigo:'E_…', mensaje }` con el mensaje de VO-010 desde el módulo de textos; estado HTTP 400/401/403/404/409/503 según familia. Las `O_*` (idempotentes) devuelven 200 con `{ ok:true, aviso:'O_…' }`.
**Rate Limiting:** solo en inicio de sesión (ver §7).

## 9. Infrastructure (Dimension 7)

**Compute Model:** un VPS o PaaS pequeño con un proceso Node (`node src/server/main.js`, sirve `dist/` y `/api`) tras un proxy inverso con TLS.
**Cloud Provider:** a elegir por el club; sin dependencia de proveedor.
**IaC:** none.
**Environments:** dev (`npx vite`, puerto 5173), test (Vitest, BD en memoria), prod.

**Config per environment:**

| Variable / endpoint | Kind | Local | Prod | Notes |
|---------------------|------|-------|------|-------|
| `DB_PATH` | path | `./data/club.db` | `/var/lib/montana/club.db` | la BD de test es `:memory:` |
| `SESSION_SECURE` | flag | `0` | `1` | activa `Secure` en la cookie |
| `PORT` / `HOST` | listener | 5173 / 127.0.0.1 | 8080 / 127.0.0.1 | detrás del proxy |
| `TRUST_PROXY` | flag | `0` | `1` | IP real para el freno de intentos |
| `/api/*` | endpoint humano | directo | tras el proxy, sin auth propia del proxy | no hay endpoints de máquina ni cron (DIM-7-003 no aplica) |

Sin credenciales externas ni cuentas de servicio (0 integraciones; DIM-7-002 no aplica).

## 10. CI/CD Pipeline (Dimension 8)

**CI Platform:** GitHub Actions: `npm ci`, `npm test`, build de Vite.
**Deployment Strategy:** direct (un solo proceso; parada breve aceptada).
**Branch Strategy:** trunk-based con ramas cortas.
**Post-deploy verification:** comprobación manual tras cada despliegue (iniciar sesión y ver catálogo) — riesgo aceptado por el tamaño del sistema; el E2E cubre el flujo antes de publicar.

---

## 11. Observability (Dimension 9)

**Logging:** JSON por línea a stdout (sin datos sensibles) + registro de seguridad de §7.
**Monitoring:** `GET /api/salud` (200 si el almacén responde) vigilado por un monitor externo gratuito.
**Alerting:** aviso por correo del monitor si cae.
**Tracing:** none.

---

## 12. Cost & Scaling (Dimension 10)

**Scaling Strategy:** static provisioning (una instancia).
**Estimated Monthly Cost:** 0–6 € (VPS mínimo).
**Cost Optimization:** sin servicios gestionados ni dependencias de pago.

---

## 13. Developer Experience (Dimension 11)

**Repo Structure:** single repo.
**Tooling:** `npm test` (Vitest, `maxWorkers: 2`), `npx vitest run {file} --maxWorkers=2`.
**Local Dev:** nativo con Node ≥ 22.13; `npx vite --host 127.0.0.1 --port 5173` levanta SPA y API con una BD local creada al primer arranque.
**Testabilidad:** `domain` sin I/O; `repo` con BD en memoria; reloj inyectable para cancelación y retrasos.

---

## 14. i18n & Accessibility (Dimension 12)

**i18n Strategy:** single language (español), i18n-ready: todos los textos salen de `src/shared/textos.js` (REQ-C-001).
**Accessibility Target:** WCAG 2.2 AA (formularios con etiqueta, errores asociados al campo, foco visible, navegación por teclado).
**Languages Supported:** es.
